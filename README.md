# CyphronTech

Marketing website for **CyphronTech**, a software development agency offering web platforms, mobile apps, AI automation, cloud engineering, and UI/UX design.

The site is a static React 18 application that is **pre-rendered to plain HTML at build time**, then takes over in the browser. Visitors, search engines and link previews get real content immediately. React is vendored as a pre-built ES module in `assets/vendor/`, and the Firebase SDK is loaded lazily from Google's CDN only after the visitor consents. It's hosted on **Firebase Hosting**.

---

## Tech stack

- **React 18.3.1**, vendored in `assets/vendor/react-bundle.mjs` (no JSX — UI is written with `React.createElement`, aliased as `h`)
- **Vanilla CSS** (`styles.css`) — no framework
- **Cloud Firestore** (Firebase Web SDK 12.7.0, lazy-loaded) for contact form submissions
- **Firebase App Check** with reCAPTCHA v3 for abuse protection
- **Firebase Hosting** for deployment (SPA rewrites to `index.html`)

The only build step is `npm run build`, which regenerates every `*.html` page (with titles, canonical URLs, social-preview tags and structured data), `404.html` and `sitemap.xml`. Run it after changing content in `src/`. `npm install` is needed once for the build tools; they are not shipped to visitors.

## Architecture

### Routing

Each `*.html` file is generated from the same React app (`npm run build`), pre-rendered for its own route. In the browser, `src/main.mjs` reads `window.location.pathname` and renders the matching page:

- `index.html` → home page (hero, services, solutions, AI approach, case study carousel, tech stack, process, FAQ, contact)
- Service files (e.g. `web-development.html`) → service detail page
- `case-*.html` files → concept case study detail page
- Legal pages and `privacy-request.html` → policy / request pages (content in `src/legal.mjs`)
- Anything else → 404 page (Firebase serves `404.html` with a 404 status; there is no catch-all rewrite)

Page content (services, case studies, tech groups, FAQ) is defined as data arrays at the top of `src/main.mjs`.

### Contact form

The contact form (`ContactForm` in `src/main.mjs`) submits to **Cloud Firestore**:

1. Input is validated and normalized client-side, with a honeypot field for bots. The visitor must tick the privacy-consent and 18+ boxes.
2. Nothing from Google loads until the visitor has accepted the small cookie notice shown on arrival (if declined, the form shows an optional opt-in checkbox and an email-draft fallback). Then the Firebase App + Firestore + App Check modules are **lazy-loaded**.
3. A validated document is written to `contactSubmissions` (name, email, project, brief, consent record). The privacy request form writes to `privacyRequests`.
4. If the visitor declines, or Firebase/App Check is not configured or the write fails, the form offers a **`mailto:` draft** to `cyphrontechllp@gmail.com`.

Firestore rules (`firestore.rules`) allow **public create-only** writes to those two collections with strict field validation, and deny all reads/updates/deletes.

> `script.js` is a standalone vanilla-JS implementation of the same header, carousel, and contact-form logic. The current pages use the React version in `src/main.mjs`; `script.js` is not referenced by any HTML.

## Running locally

Because the app uses ES modules and Firebase imports, it must be served over HTTP — opening `index.html` via `file://` will not work.

```bash
# Any static server works, e.g.:
npx serve .
# or
python -m http.server 8000
# or
firebase serve
```

Then open the served URL (e.g. `http://localhost:8000`).

## Firebase / contact form setup

See **[FIREBASE_SETUP.md](FIREBASE_SETUP.md)** for full details. In short:

1. Enable Cloud Firestore in the Firebase Console.
2. Copy `assets/firebase-config.example.js` to `assets/firebase-config.js` and fill in your Firebase Web App config.
3. Set `contactFormSettings.enabled` to `true`.
4. Deploy `firestore.rules`.
5. Register a reCAPTCHA v3 key and add the public site key to `contactFormSettings.appCheck.siteKey`, then enable App Check. Firestore writes are intentionally refused (with `mailto:` fallback) until App Check is configured.
6. Restrict the Firebase Web API key to your domains and keep the Hosting CSP in `firebase.json` aligned with your module sources.

Only the **public** Firebase Web config belongs in the static site. Never commit service-account keys, Admin SDK credentials, or reCAPTCHA secret keys.

## Deployment

**Firebase Hosting** (project `cyphrontech-app-v2`). Deploy rules and hosting together, because the form fields and rules change together:

```bash
firebase deploy --only firestore:rules,hosting
```

This serves the repo root as static hosting, applies the CSP and security headers, and rewrites all routes to `index.html`. It ignores config/docs files listed in `firebase.json`.

See `COMPLIANCE.md` before going live: it lists business details and legal assumptions that need your confirmation.
